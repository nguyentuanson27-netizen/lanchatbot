## Goal and owners

Help the customer choose and buy a suitable product through grounded advice,
without losing a clause, repeating known inputs or treating interest as authority.
Producer interprets the latest customer delta. Strategist chooses the answer,
evidence and at most one useful next input. Responder realizes that task naturally.
Code owns catalog/policy facts, comparisons, cart mutation, checkout fields and
effect authorization. Scripted model responses in tests are not evidence of
real-model comprehension, persuasive quality or conversion.

## P06: one-product transaction and compound input

On the typed pre-sale path, a policy question no longer suppresses an independent
validated purchase/edit/checkout/confirmation. Conditional purchase remains
non-committed; a policy-only question does not create a cart. The policy answer is
retained alongside the existing code-owned transaction response. C3 does not
replace that response with another strategy.

After extraction, downstream model consumers receive the same updated session
budget/occasion/rejections as C3. A referential rejection binds to the product
current before the turn. Selecting another product clears dependent considered
variant/fit/order-draft context; the existing cart keeps its independent identity.
Typed stage selection does not re-run the legacy whole-message buying trigger.
Legacy C3-off behavior remains covered by the unchanged regression cases.

Variant edits require the same line, parent, offer, quantity and components.
Each component must have the requested size/color and retain the other field
when it was not requested. Both-field edits must match both. This uses the
existing SET_LINE_VARIANT/reprice/readiness path; no new mutation command exists.

For a verified fact question combined with a purchase, when checkout is still
missing fields and no preview exists, retain the already-guarded product answer
and append the code-owned missing-checkout request. In the regression 'choose M,
is S available?', S stock is PRODUCT evidence, not CART evidence for M. The
pending cart summary is not repeated in that narrow turn; mandatory preview and
confirmation forms are unchanged. Product outbound readiness and cart mutation
readiness remain separate and are rechecked before the existing atomic commit.
This is not a general permission to combine arbitrary product and cart claims.

Tests cross RealtimeRunner -> validated typed input -> sales cycle -> final
reply/state: purchase plus policy -> recipient/COD -> preview -> confirmation,
CHANGE plus purchase, selected M with stock question S, and human/post-sale
requests while a cart is open. Existing source/confidence/recipient/duplicate/
stale-preview/human-owner no-call tests are retained. External model, POS, inbox
and delivery ports are fakes. PURCHASE_CONFIRMED is internal state, not a receipt
that an external POS order was created.

## P07: relevant advice, resumed questions, known first-contact input

The central prompt now distinguishes a new topic from a short answer/corrected
code completing an earlier clarification. It requests resolution of the open
question on the corrected binding before acknowledgement. Price objections
separate a known budget cap, value concern, comparison and conditional offer;
none automatically authorizes a discount, search or purchase. Responder remains
execution-only, without new factual wording authority.

The fixed first-contact form stays intact. Known offered color is not asked
again; height/weight requests name only the missing field. If all applicable
inputs or verified fit evidence are present, KEEP_OPEN ends without a question.
This is the explicit candidate amendment to section 1 of the C3 spec, not an
interpretation that the former exact-one-question rule already allowed zero.
No product/price/permission policy or provider configuration changes.

Request/compiler/egress tests exercise known and missing input, and a clarified
material question beyond the previous 15-message window with supported and
unresolved evidence. These scripted tests establish contract behavior, not that
a particular model will choose the right strategy or sound natural in all cases.

## P08a: alternatives from a bounded verified shortlist

Explicit typed SEARCH/REJECT uses the existing search adapter. The query includes
current budget/occasion and latest customer text; current and previously rejected
product IDs are excluded. Close similarity scores may form a discovery shortlist
without being treated as an exact product identification. Identity search itself
is unchanged. Shortlist results are not cached as commercial authority.

At most three unique candidates are checked through the existing POS facts reader.
Only fresh, correctly bound price/offer/positive-stock results within a known
budget may be suggested. A result is a suggestion, not a cart commitment. Failed
lookups and no matching verified candidate are distinguished. No-result wording
is scoped to the candidates just searched, not the entire catalog. Color edits
stay on the variant path rather than triggering alternative search.

The search is bounded, not an exhaustive guarantee that a suitable item does not
exist. Other customer criteria still require catalog evidence and strategist
judgment; no unverified quality/fit property is inferred from similarity.

## P08b: scoped price comparison

Code derives ordering/equality/difference only from independent validated POS
fact envelopes that match current PRICE claims, products, versions and freshness.
Both operands must use the same offer kind and one parent-product offer as unit,
with VND currency. Missing/duplicate/stale/changed/mismatched operands omit the
comparison while preserving eligible independent facts.

`comparisonFacts` is a code-owned optional input to the existing compiler/guard,
not a Strategist field, a Context V2 authority migration, or a model annotation.
Admission and egress independently recompute the deterministic comparison. Final
outbound readiness binds its underlying PRICE sources. Cheaper never implies
better quality or value; comparisons of other attributes require their own
existing evidence. No online semantic-review model was added.

## P09: reuse current accepted history and known customer context

Remove the second 14-15-message cut: reuse the existing history reader's 30
messages plus current inbound and one bounded customer-context event (maximum 32).
The shared request validator applies the same finite bound and existing per-
message privacy/length checks. Frozen DEV70 data/rubric are unchanged.

The context event labels customer-reported budget/occasion/rejections,
measurements, preferences and current selection. Existing privacy/URL redaction
runs before model input. These fields cannot establish shop facts or completed
effects. No new history read, summarizer call, table, store or durable memory
schema exists. Short dialogues retain their content; corrected session values
are current rather than copied from stale summaries.

Accepted-Outbox recovery and no-resend behavior are unchanged and remain in the
regression suite. Pending/failed send is not promoted into accepted bot history.
History older than the existing 30-message source limit is still unavailable
unless already captured by profile/session. This patch does not claim unlimited
memory or retention of every old question/reason.

## Deliberate compatibility changes and limits

Changed only where this amendment specifies: policy plus independent commerce,
strict variant-field preservation, compound fact/purchase answer ownership,
bounded verified discovery, independent price comparison, retained existing
history, and non-repetitive first-contact inputs. Media/URL ownership branches,
external effects, database CAS/fencing, page allowlist and live provider selection
are not refactored. C3-off and human-owner controls remain intact.

Real-model P05/P11 evaluation, DEV70, latency/token-cost comparison, wider
multi-product cart journeys and remaining P10 fault-injection acceptance are not
certified by this patch. Exact new-head CI is required after owner push. A green
baseline run does not certify the exported source. Apply and roll back this
source-only patch as one reviewed unit; no migration or live rollback is needed.
